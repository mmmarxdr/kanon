## Exploration: Settings UX Polish + IA Restructuring (layout, theme, a11y)

> **Update (2026-08-03, same day)**: This exploration was updated after the user issued locked product decisions ("mandale") that change the information architecture (IA) of the settings surfaces, in addition to the original layout/theme/a11y polish scope. The polish findings from the first pass are preserved below; a new "Locked Product Decisions" section captures the IA changes and supersedes any IA assumptions in the original scope (e.g. the original acceptance criterion "no functional regressions to ... domains ... notifications ... flows" is superseded — those flows are being intentionally relocated, not merely polished).

### Locked Product Decisions

These are **not open for debate in this change** — they were decided by the user and are recorded here as the contract for `sdd-propose`/`sdd-spec`/`sdd-design`:

1. **Instance owns email/signup domain policy on `/admin/instance`.** No "Allowed Domains" peer tab for ordinary users on `/settings`. This is already partially true today — `admin.instance.tsx` has its own `allowedSignupDomains` field (instance-wide open-signup gating) that is functionally distinct from the workspace-level feature in decision 2.

2. **Workspace `allowedDomains` leaves the common Settings IA (Members/Invites/Integrations peer-tab row).** Two options were presented — **Option B is selected**: owner-only secondary affordance with distinct invite copy, not full removal (Option A rejected). Rationale, backed by code investigation:
   - `Workspace.allowedDomains` is **not decorative** — `packages/api/src/modules/invite/service.ts:110-123,517-523` shows `isDomainAllowed()` is enforced at invite-acceptance time (`DOMAIN_NOT_ALLOWED` 403), gating who can join a workspace via a shared invite link. It is functionally distinct from the instance-level `allowedSignupDomains` (which gates open self-service signup, not invite acceptance) — these are two different mechanisms and must not be visually conflated.
   - Because the feature is live and enforced, Option A (delete the tab, no replacement) would silently strip workspace owners of their only way to view/edit an active security control — a functional regression, not just a decluttering.
   - The feature is **only ever relevant in the context of creating/managing invites** (it has no effect anywhere else), so the natural home is inside the Invites surface rather than as an equal-weight peer tab. Recommendation: an owner-only, collapsed-by-default secondary panel/disclosure inside `invites-section.tsx` (reusing `domains-section.tsx`'s existing add/remove-domain logic and API calls, just relocated), with copy that explicitly disambiguates it from instance-wide signup policy — e.g. "Restrict who can join via invite link" rather than reusing any copy that could be confused with `/admin/instance`'s "Allowed signup domains" field.
   - This satisfies decision 1 (no peer tab) while avoiding a functional regression.

3. **Notification preferences move from `/settings` to `/profile`.**
   - Important architecture note: `useNotificationPreferencesQuery`/`useUpdateNotificationPreferencesMutation` are **per-user-per-workspace**, not purely global (`GET /api/workspaces/:id/notification-preferences` — see `use-notification-preferences-query.ts:6-14`). `/profile.tsx` today has **no workspace context** (it's a flat global page: display name, avatar, change password).
   - Recommendation for this slice: reuse the existing globally-available `useActiveWorkspaceId()` hook (`hooks/use-workspace-query.ts:33`, backed by a Zustand store, already used outside of `/settings`) to scope the relocated `NotificationPreferencesSection` to the user's current active workspace, with a small contextual label (e.g. "For workspace: {name}") so users understand these prefs are workspace-scoped even though the page itself isn't. Building a full multi-workspace notification-settings table is explicitly **out of scope** for this slice — flag as a follow-up if multi-workspace visibility is later requested.
   - `NotificationPreferencesSection` itself needs no logic changes — it's a relocation, not a rewrite.

4. **Ownership boundary**: Members + Invites = workspace; Project Members = project; Redmine bootstrap/maps = instance admin.
   - Members (`members-section.tsx`) and Invites (`invites-section.tsx`, now absorbing the domain-restriction affordance from decision 2) stay on `/settings`.
   - `ProjectMembersSection` stays on `/project-settings/$projectKey` (unchanged — already project-scoped).
   - Redmine **bootstrap connection + status/time-activity provider maps** (`admin-redmine-section.tsx`) stays on `/admin/instance` (unchanged — this is already where it lives today, confirming the current placement is correct).
   - **Not explicitly covered by decision 4, flagged for propose-phase confirmation**: the *workspace* "Integrations" tab's `redmine-section.tsx` (personal API-key connect/disconnect via `CredentialCard`, Kanon-project↔Redmine-project binding via `ProjectBindCard`, and a workspace-admin coverage dashboard via `CoverageCard`) is a third, separate Redmine surface not named in decision 4. My working interpretation is that it is unaffected and remains on `/settings` under "Integrations" — it's neither "bootstrap/maps" (that's the admin-only service-credential + status-mapping flow) nor "members/invites". `sdd-propose` should explicitly confirm this interpretation with the user before finalizing IA scope, since it's the one ambiguous surface.

**Resulting `/settings` tab set after this change**: Members, Invites (with the new owner-only domain-restriction disclosure), Integrations (Redmine, personal connection/binding/coverage) — **3 tabs**, down from 5. This changes the shape of the layout-polish work below: with Domains and Notifications gone, the previous `maxWidth: activeTab === "integrations" ? 960 : 720` split now only distinguishes Integrations from the remaining two (Members/Invites), which reinforces (rather than removes) the case for a single, viewport-responsive width rule instead of hand-picked pixel caps per tab.

### Current State (original polish findings — still valid)

Three independent settings-like surfaces exist, each with its own page shell and no shared layout primitive:

1. **Workspace Settings** — `packages/web/src/routes/_authenticated/settings.tsx`
   - Page chrome (header, tab strip, body wrapper) is hand-rolled with inline `style={{ ... }}` using raw `var(--bg)`, `var(--line)`, `var(--ink*)`, `var(--accent)` tokens — the codebase's "new" pattern (see `index.css` comment: "The new code uses the raw `var(--*)` tokens directly").
   - Body wraps children in `maxWidth: activeTab === "integrations" ? 960 : 720`. After the IA changes in this update, this split now applies to 3 tabs (Members/Invites at 720, Integrations at 960) instead of 5 — the inconsistency is smaller in surface area but still present.
   - Tabs (`TAB_KEYS.map(...)`) are plain `<button>` elements in a flex row with zero ARIA: no `role="tablist"`/`role="tab"`, no `aria-selected`, no `id`/`aria-controls` pairing to a panel, no roving `tabIndex`/arrow-key navigation. A codebase-wide grep confirms `role="tab"` does not appear anywhere in `packages/web/src` — this is the only tab-like control in the app and it has no accessible-tabs pattern to inherit.
   - Renders section components that each independently re-implement the exact same Tailwind-utility card shell: `className="rounded-lg border border-border bg-card p-6"` (members-section.tsx:76, invites-section.tsx:122) or `p-5 sm:p-6` (redmine-section.tsx:15, admin-redmine-section.tsx:60, via a locally-duplicated `Card` helper function in each file). `domains-section.tsx`'s card shell is being absorbed into `invites-section.tsx` per decision 2, not eliminated as a separate surface.

2. **Project Settings** — `packages/web/src/routes/_authenticated/project-settings.tsx`
   - Also uses raw `var(--*)` inline styles for the page chrome, `maxWidth: 720`, no tabs (single section only: `ProjectMembersSection`). Unaffected by the IA decisions (confirmed workspace/project boundary, decision 4).
   - `ProjectMembersSection` (`packages/web/src/features/project-members/project-members-section.tsx`) uses the same Tailwind-utility card shell as the workspace settings sections — i.e. structurally near-identical member-list UI is duplicated between `members-section.tsx` and `project-members-section.tsx` with no shared component.

3. **Instance Admin** — `packages/web/src/routes/_authenticated/admin.instance.tsx`
   - Fully inline `var(--*)`-styled (no Tailwind utility classes at all): custom input wrappers (`height:36, border:1px solid var(--line-2), background:var(--panel)`), custom buttons, a different `maxWidth: 560`. This is visually and structurally a *third* distinct settings layout system, diverging from both #1 and #2. Confirmed by decision 1/4 as the correct home for instance-wide signup/domain policy and Redmine bootstrap/maps — no IA change here, only polish.
   - `AdminRedmineSection` (rendered at the bottom of this page) reverts to the Tailwind-utility card style used in workspace settings — so a single page mixes the "new" raw-token style and the "old" Tailwind-utility style within one scroll view.

4. **Profile** — `packages/web/src/routes/_authenticated/profile.tsx` (newly in scope per decision 3)
   - Already Tailwind-utility styled (`rounded-lg border border-border bg-card p-6`, matching the "old" settings-sections convention, not the raw-var convention used by the settings/admin page shells) — `maxWidth: "lg"` (Tailwind `max-w-lg` ≈ 512px) via `className="mx-auto max-w-lg space-y-8"`, a **fourth** distinct width choice once notification preferences move here.
   - Has its own instances of the same hardcoded-color anti-pattern found elsewhere: `profile.tsx:188` and `:284` — `"rounded-md border border-green-500/50 bg-green-500/10 ... text-green-700"` for profile-save and password-change success banners. Same dark-mode contrast risk as the invites/redmine badges below.
   - No workspace context today (see decision 3 discussion above) — this is the one piece of net-new plumbing this change requires beyond straight relocation/polish.

**Layout summary** — four different max-width values now in scope: `720` (workspace settings Members/Invites, project settings), `960` (workspace settings Integrations), `560` (instance admin), `~512` (`max-w-lg` on profile). None scale with viewport; all are fixed caps that leave visible dead space on wide screens, matching the reported "wasted space" complaint.

**Theming** — `index.css` defines OKLCH tokens (`--bg`, `--ink*`, `--accent`, `--ok`, `--bad`, etc.) with light/dark handled via `[data-appearance="dark"]` overrides (set by `stores/theme-store.ts` on `document.documentElement.dataset.appearance`), and a Tailwind v4 `@theme` bridge that maps semantic Tailwind classes (`bg-card`, `text-foreground`, `bg-secondary`, `border-border`, `bg-destructive`, `text-destructive`) onto those same OKLCH variables. **The bridge itself is complete and correct** for every bridged class actually used across these surfaces — `bg-card`/`text-foreground`/`bg-secondary`/`border-border`/`text-destructive` all resolve through tokens and do repaint correctly across light/dark and the three theme palettes (cobalt/teal/mono).

The real theme bugs are **hardcoded Tailwind default-palette utilities that bypass the bridge entirely** (not part of `@theme`, so they never move with `data-appearance`/`data-theme`) — **6 occurrences now confirmed** (2 more found in `profile.tsx` since it entered scope via decision 3):
- `invites-section.tsx:43` — `className: "bg-green-500/10 text-green-700"` for the "active" invite status badge.
- `redmine-section.tsx:131` — `text-emerald-600` for a bind-success message.
- `redmine-section.tsx:239` — `"rounded-full bg-emerald-500/10 px-2 py-1 text-xs font-medium text-emerald-600"` for a bound-project badge.
- `admin-redmine-section.tsx:208` — `text-emerald-600` for a maps-saved success message.
- `profile.tsx:188` — `"rounded-md border border-green-500/50 bg-green-500/10 px-3 py-2 text-sm text-green-700"` for the profile-save success banner.
- `profile.tsx:284` — same pattern for the password-change success banner.

In dark mode these render literal Tailwind gray-scale-independent greens (`green-700`/`emerald-600` are mid-dark hues) against the dark `--panel` background (`oklch(0.21 ...)`, near-black) with materially reduced contrast versus every other status color in the app (which all route through `--ok`/`--bad`/`--warn` and get dark-mode-tuned lightness bumps, e.g. `--ok: oklch(0.62 ...)` light → `oklch(0.74 ...)` dark). This is a genuine "looks wrong in dark mode" defect, not a false lead. There is codebase precedent for treating this as a real bug class: commit `1b66834 fix(web): replace hardcoded bg-[#E8E8E8] with bg-background token in form controls` already fixed an analogous hardcoded-color issue.

Secondary, lower-severity hardcodes (style inconsistency, not necessarily a visible dark-mode bug): `bg-white` toggle-knob in `notification-preferences-section.tsx:92` (works acceptably in both modes today but isn't tokenized — travels to `/profile` unchanged per decision 3), and `text-white` on destructive confirm buttons (`members-section.tsx:183`, `project-members-section.tsx:246`) where `text-destructive-foreground` (bridged to `--btn-ink`) would be the consistent choice.

**Accessibility** — beyond the tab-strip issue above:
- Notification toggles (`notification-preferences-section.tsx:74-96`) use `role="switch"` + `aria-checked` correctly, but the clickable `<button>` has no `aria-label`/`aria-labelledby` tying it to its adjacent label text (`<p>{t(labelKey)}</p>` at line 100 is a sibling, not referenced via `id`/`aria-labelledby`) — screen readers announce "switch, checked/unchecked" with no name. This travels to `/profile` unchanged unless fixed as part of this same change.
- The same switch uses `focus:ring-2 focus:ring-primary focus:ring-offset-2` with no explicit `ring-offset-*` color utility, so the offset ring falls back to Tailwind's default offset color; this should be verified visually against dark `--bg` (needs browser check, flagged as a risk below rather than a confirmed bug).
- Destructive actions (remove member, revoke invite, remove domain) use inline "Remove" → "Confirm/Cancel" swap without `aria-live` announcement of the state change, and no keyboard-escape-to-cancel.
- Dense list rows throughout (members, invites, project members) pack avatar + name + email + role + 1-2 buttons into a single 36-40px-tall flex row with small (11-12px) text — this is the "dense cards, weak affordances" complaint; it's a design-density issue more than a strict a11y violation, but contributes to the "feels unfinished" impression.

### Approaches

1. **Per-page targeted fixes (no shared primitive), IA changes applied minimally in place** — implement decisions 1-4 as direct edits to existing files (remove Domains tab, move domain UI into invites-section.tsx inline, move NotificationPreferencesSection into profile.tsx as-is, fix the 6 hardcoded colors, add toggle aria-label) without introducing any new shared component.
   - Pros: Smallest diff, lowest risk, no new abstraction to design/review.
   - Cons: Leaves 4 divergent page-shell/width implementations and duplicated card-shell/member-row code in place; doesn't address the "wasted space" complaint holistically.
   - Effort: Low-Medium (the IA moves are mechanical; the polish is separable).

2. **Shared settings shell + card primitives, migrate all 4 surfaces (incl. profile)** — introduce a `SettingsShell`/`SettingsPage` layout component (header + optional accessible tabs + responsive width) and a `SettingsCard` primitive in `components/ui/`, written in the "new" raw-`var(--*)` style to match `primitives.tsx` conventions; migrate `settings.tsx`, `project-settings.tsx`, `admin.instance.tsx`, and the relevant portion of `profile.tsx` onto it; apply the IA decisions and color/a11y fixes as part of the same change.
   - Pros: Fixes the root cause instead of symptoms; guarantees future settings surfaces inherit correct theming/a11y for free; standardizes responsive width instead of guessing at four different pixel caps; consolidates the accessible-tabs pattern in one place.
   - Cons: Largest diff — touches four route files plus a new shared component and the IA relocation in the same change; highest review surface, will need chaining per the 400-line PR budget guard; highest regression risk since chrome, IA, and theming all move together.
   - Effort: High.

3. **Hybrid — shared primitives for the clear duplication, IA changes as their own slice, admin/profile left structurally as-is (RECOMMENDED, unchanged conclusion from before)** — build the `SettingsCard` primitive and the accessible tab pattern for `settings.tsx` (the one page with real tabs) and migrate the Tailwind-styled section cards onto it; leave `admin.instance.tsx`'s fully-custom raw-var layout structurally as-is (only fixing `maxWidth`/colors); leave `profile.tsx`'s existing Tailwind-card structure as-is (only adding the relocated notification section + fixing its 2 hardcoded colors) rather than forcing it onto the new `SettingsCard` primitive in this pass.
   - Pros: Captures most of the value of Approach 2 with a smaller, easier-to-review diff; cleanly separates "IA decisions" (functional relocation, must not regress `DOMAIN_NOT_ALLOWED` enforcement or notification-preference semantics) from "presentation polish" (shared card/tabs/tokens), which are two different risk profiles and should get two different review passes.
   - Cons: Kanon still ends up with more than one page-shell convention by design; some inconsistency remains.
   - Effort: Medium.

### Recommendation

**Approach 3 (hybrid)**, phased as chainable PR slices to respect the 400-line review budget — reordered from the original exploration to put the now-locked IA decisions first, since they're product-mandated and unblock the layout work (fewer tabs = simpler layout math):

- **Slice A — IA relocation (functional, decisions 1-4)**: remove the Domains tab from `settings.tsx`; add the owner-only domain-restriction disclosure to `invites-section.tsx` (reusing `domains-section.tsx`'s existing mutation logic); relocate `NotificationPreferencesSection` from `settings.tsx` to `profile.tsx` wired to `useActiveWorkspaceId()` with a workspace-context label. Verify `DOMAIN_NOT_ALLOWED` invite-acceptance behavior and notification-preference read/write are unchanged end-to-end (existing tests + manual smoke). This is the highest-risk slice functionally (real behavior relocation) so it should be reviewed and merged independently before any pure-polish work lands on top of it.
- **Slice B — token/contrast bugfixes**: all 6 hardcoded Tailwind-palette colors (now including the 2 in `profile.tsx`), toggle `aria-label`, `text-white` → `text-destructive-foreground`. Small, isolated, no layout risk, can ship in parallel with or right after Slice A.
- **Slice C — accessible tabs for `settings.tsx`** (now only 3 tabs: Members/Invites/Integrations) — roles, `aria-selected`, `id`/`aria-controls`, roving tabindex + arrow-key nav — plus a unified responsive width for the (now-simpler) workspace-settings body, replacing the `720`/`960` split.
- **Slice D — extract `SettingsCard`** and migrate the duplicate card-shell call sites (members, invites, project-members, redmine, admin-redmine) — mechanical, no test coupling to exact class strings (confirmed by grep), safe to do independently of Slice C.
- `admin.instance.tsx` and `profile.tsx` get only Slice B-scope color fixes plus their respective Slice A relocations — no shell migration in this change, per Approach 3's rationale.

This ordering lets `sdd-propose`/`sdd-tasks` size each slice independently, front-loads the functional/product-mandated change (Slice A) so it can be validated on its own before pure polish stacks on top, and still lets Slice B ship fast as a high-confidence fix for the most visible dark-mode complaint.

### Risks

- **Slice A is a functional relocation, not pure polish** — must not regress `DOMAIN_NOT_ALLOWED` invite-acceptance enforcement (`packages/api/src/modules/invite/service.ts`) or the per-workspace semantics of notification preferences. Needs explicit manual/automated verification, not just visual QA.
- **`/profile` has no workspace context today** — introducing `useActiveWorkspaceId()` there is new plumbing (small, but net-new) for a page that was previously workspace-agnostic; if a user has zero workspaces or the hook returns `undefined`, the relocated `NotificationPreferencesSection` needs a defined empty/disabled state (today's `settings.tsx` handles this via the parent's `!workspaceId` early return, which profile.tsx does not have).
- **Ambiguous ownership of workspace-settings `redmine-section.tsx`** — decision 4 does not explicitly name this surface; the working interpretation (unchanged, stays on workspace settings) should be confirmed explicitly during `sdd-propose` rather than assumed silently through to `sdd-apply`.
- **Visual regression across 3 themes × 2 appearances × 4 surfaces** (now including `/profile`) — any shell/card change must be manually checked in cobalt/teal/mono × light/dark before merge; no automated visual regression tooling was found in this repo for the web package.
- **`ring-offset` default color on the notification toggle's focus ring** was not confirmed as broken (needs a real-browser check against `--bg` dark) — flagged as unverified, not asserted as a bug; design phase should verify before scoping a fix.
- **Instance admin is super-admin-gated** — manual QA of that page requires a super-admin test account; confirm test/dev fixtures support this before relying on visual QA alone.
- **`project-members-section.tsx` has a `TODO(PR4): pm assignability UI ... deferred to PR4`** (line 15) — any refactor of that file's card shell must not touch the deferred-scope role-dropdown logic, to avoid scope creep into an unrelated pending change.
- **400-line PR budget** — Approaches 2/3 both risk exceeding budget if done as one PR; delivery_strategy is `ask-on-risk`, so `sdd-tasks` MUST forecast per-slice line counts and flag `Decision needed before apply` if a slice risks exceeding 400 lines. **400-line budget risk: Medium** — Slice A (functional relocation across 3 files) and Slice D (7-file card-shell migration) are the most likely to need further splitting.
- **No shared `Tabs`/`Switch` component exists today** — building the accessible tab pattern is net-new code (not just a migration), so it should get its own focused review pass rather than being folded into the card-shell extraction.
- **Existing i18n keys** (`domainsTitle`, `domainsHelp`, etc. in the `settings` namespace) were authored assuming Domains is a standalone tab — moving this UI into `invites-section.tsx` will need new/adjusted copy keys per decision 2's "distinct invite copy" requirement; not just a straight component move.

### Ready for Proposal

**Yes.** The locked product decisions resolve the previously-open IA questions (decision 2's A-vs-B choice is now made: **Option B**, with concrete rationale grounded in the `isDomainAllowed()` enforcement code), the ownership boundary is documented with one flagged ambiguity for `sdd-propose` to confirm (workspace-level `redmine-section.tsx`), and the phased hybrid recommendation (4 chainable slices, functional relocation first) fits the project's 400-line PR budget guard. `sdd-propose` should scope Slice A (IA relocation) first as the product-mandated, highest-priority deliverable, with Slices B/C/D following as a chained-PR set per `chained-pr` conventions.
